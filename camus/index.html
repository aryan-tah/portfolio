Case study · Open-source contribution · November 2026

Making a Kafka broker's cloud bill something you can measure.

Camus is a broker that speaks Apache Kafka's protocol in one Rust binary and keeps its log in Cloudflare R2: no JVM, no ZooKeeper. Its design included a cost model for R2, but nothing measured it. I contributed the metrics that do, and wrote proposals for what a team would need next. Camus is Nidheesh Vakharia's project; this is about my part.

01

Three questions nobody could answer.

Anyone running a message broker asks three things first. How far behind is each consumer? How far behind is the uploader? And for a broker that stores everything in R2: how many paid requests are we sending, and what will that cost?

Camus exported about a dozen metrics, none of which answered those. Its design notes had a cost model for R2 requests, but nothing in the running system measured it. I wrote that up as an issue, then fixed it.

02

What I built.

ACount every object-store call.

Puts, gets, heads, lists and deletes, plus errors and bytes in and out, exported as eight fixed counters. A retry or a paged list counts as one call, so the numbers match what R2 bills.

Why fixedNo per-key or per-object labels. Metrics with unbounded labels are how monitoring takes down the thing it's monitoring.

BShow every write-ahead-log shard.

Unsealed bytes, leadership and storage failure, for every shard. Before, only the first shard's numbers existed, and only in an admin JSON endpoint.

BoundedOne series per shard, and the shard count is fixed when the cluster starts.

CFix the tests that were already failing.

Two tests were flaky on CI and failing on main: a write after a leader election, and a consumer group rebalance. I fixed both in the same pull request.

ProofRan the failover test 30 times with no failures before calling it fixed.

03

What I proposed next.

  • Scaling without moving partitions by hand. An RFC on adding and removing brokers, and what storing data in R2 makes cheap that Kafka makes expensive.
  • Quotas and per-team usage. An RFC for per-principal limits and usage numbers, which any shared or hosted cluster needs.
  • Operability. Proposals for a Helm chart, a rolling-upgrade test under load, a restore drill, a cost calculator, and testing popular Kafka web consoles against Camus.

04

What I learned.

  • Read the cost model before the code. The most useful metric was the one the design already promised.
  • Leave the build greener than you found it. A metrics PR that also fixes two failing tests gets reviewed faster.
  • Ask the operator's questions. Lag, upload lag and cost are what someone on call needs at 3am. Start there, not with whatever is easy to count.
