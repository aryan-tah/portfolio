Case study · Vennbee · March to October 2026

Moving a social graph into Postgres without rewriting the app.

Every vouch, membership, nested community and reply thread in Vennbee is a graph. We started on Neo4j, swapped it for Postgres running Apache AGE, and then moved the hottest reads to plain SQL. The slowest one went from about ten seconds per result to a few milliseconds.

01

What the graph is for.

Vennbee is built on relationships: who vouches for whom, who belongs to which community, which community sits inside which, and which message replies to which. The feed, friend-of-friend suggestions, “your spaces” and search ranking all read that graph.

In March I set up Neo4j and a background worker that mirrors every change from Postgres into it. Postgres stays the source of truth; the graph is a copy shaped for questions like “how close is this person to me?”

02

The principles.

  • The graph is a mirror. Everything in it can be rebuilt from Postgres, so it never needs transactions with the main database, and losing it is an inconvenience, not a disaster.
  • Postgres first, then sync. Writes land in Postgres and a queue carries them to the graph. The app never waits on the graph to save something.
  • Keep the query language. If the new store speaks the same Cypher, the app's queries don't have to change.

03

Five decisions.

ASwap the engine, not the app.

Running a separate Neo4j instance meant another system to operate. Apache AGE adds openCypher to Postgres, so the graph could live in a database we already knew how to run, while the app kept its queries and its sync worker.

CostAGE's Cypher isn't Neo4j's. Every gap in the dialect became something to work around.

BSpike before committing.

Before migrating, a small spike ran the real queries against AGE. It found four gaps: an update after a merge silently did nothing, two kinds of syntax weren't supported, and one sort didn't work. Each got a workaround before anything moved.

WhySilent no-ops are the dangerous kind. Better to find them in a spike than in production data.

CRebuild from Postgres, then compare.

Instead of exporting from Neo4j, the new graph was rebuilt from the source of truth, and a parity check compared the two before cutover.

CaughtIts first run found memberships of deleted profiles handled differently on each side. The check was the go/no-go gate.

DKeep a way back.

The old graph stayed available during the cutover, so switching back was a configuration change, not a migration.

CostTwo graph stores to keep in mind for a while.

EMove the hot paths to SQL.

As the graph grew, reranking search results by closeness took about ten seconds per result and ran the connection pool dry. I rewrote it as indexed SQL: 3 to 6 milliseconds. The feed's membership check moved to a direct Postgres lookup too.

LessonA graph database is great for exploring relationships. For the two or three questions you ask on every request, an index in Postgres usually wins.

04

The bug that looked like flaky phones.

After the swap, “your spaces” sometimes came back empty on mobile. Not always: only when the graph answered faster than Postgres.

The cause was small. Postgres lowercases unquoted names, so a column called spaceId came back as spaceid, and the app read undefined. It only showed up when the graph won the race. The fix was to quote names in one central place, so no query could hit it again.

06

What I'd do differently.

  • Benchmark the hot path, not the engine. The question was never Neo4j versus AGE. It was which three queries run on every request, and what they need.
  • Put the parity check in from day one. A mirror you can't verify is a mirror you can't trust.
  • Start with SQL for anything simple. Most of what made the app fast in the end was ordinary Postgres with good indexes.
